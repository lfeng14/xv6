- As a reminder, RISC-V instructions (both user and kernel) manipulate virtual addresses.
- 相同的虚拟地址 如何通过页表项 映射到不同的物理地址
  - 这个区分点在CPU的“页表根地址寄存器”里。每个进程的页表有独立的根页表，进程切换时，内核会把当前进程的根页表物理地址写入这个寄存器。这样CPU翻译虚拟地址时，会从当前寄存器指向的根页表开始查找，自然就区分了不同进程的虚拟地址空间。

- 如图3.2所示，RISC-V CPU 分三步将**虚拟地址**转换为**物理地址**。
  页表以**三级页表树**的形式存放在物理内存中：
  - 根节点是一个4096字节的页表页，包含512个页表项（PTE），指向二级页表页；
  - 每个二级页表页同样存512个PTE，指向最终的三级页表页。
  地址翻译时，27位虚拟地址被分为三段各9位：
  - 高9位：在根页表页中选一个PTE；
  - 中9位：在二级页表页中选一个PTE；
  - 低9位：定位到最终的PTE，完成三级寻址。

  - **个人理解**：输入一个虚拟地址，将虚拟地址拆分后(L2 L1 L0 offset) 分别去三个层级的page table查找PPN，最后拼接起来就是物理地址。
  - 从虚拟地址拆分、逐级查找页表项，到发现PPN不存在触发页错误(**page fault**)，这个过程都是**硬件自动完成**的。软件只负责在页错误发生后进行处理，比如分配物理页、更新页表等。
  - TLB miss 这种是因为页表项太多，还是因为它老是在跳来跳去？**两种情况都可能导致 TLB miss**。如果程序访问的虚拟地址范围很大，页表项数量超过 TLB 容量，就会因为 TLB 存不下而频繁替换旧项，导致 miss；如果程序频繁在不同虚拟地址区域跳转，比如多进程切换或频繁调用不同函数，TLB 里缓存的页表项刚加载就被新的替换，也会增加 miss 率。实际中，进程切换是导致 TLB miss 的常见场景之一，因为切换后 TLB 里的旧进程页表项基本失效了。
  - 页表项是软件内核控制的。进程切换时，内核会把新进程的页表基地址写入 CR3 寄存器，硬件才会根据新的 CR3 去查找新进程的页表。所以页表的切换是内核通过修改控制寄存器触发的，属于软件操作。页表基地址是进程上下文的重要部分，内核切换进程时必须保存旧进程的 CR3 值，再加载新进程的 CR3 值，这样才能保证新进程使用自己的页表。

- SATP 寄存器是 RISC-V 架构里的 “超级特权地址转换和保护寄存器”，主要存页表的物理基地址，还会指定页表级数和地址转换模式。当 CPU 需要把虚拟地址转成物理地址时，就从 SATP 寄存器里拿页表基址，开始一级级查页表。它就像页表的 “总开关”，控制着虚拟内存转换是否开启。也是进程的上下文信息。
- 也就是进程执行的指令是包含虚拟地址的，比如load x，实际执行时通过mmu硬件单元真实操作物理内存。

- 物理地址空间被划分为两段：低段（< 0x80000000）是“设备寄存器”的窗口，高段（0x80000000 ~ PHYSTOP）是真正的 DRAM。内核通过普通的读写指令访问设备，但必须小心区分目标地址属于 RAM 还是 MMIO。
- 内核通过**直接映射**访问内存与内存映射设备寄存器，即虚拟地址与物理地址完全相同。
例如内核自身在虚拟地址空间和物理内存中均位于 `KERNBASE=0x80000000`。
这种方式简化了内核读写物理内存的代码：
如 `fork` 为子进程分配用户内存时，分配器返回物理地址，`fork` 可直接将其作为虚拟地址，完成父进程内存到子进程的拷贝。
- 内核中存在两类非直接映射的虚拟地址：
  - 1. **跳板页（trampoline page）**：映射于虚拟地址空间顶部，用户页表也有相同映射；其对应的物理页在内核虚拟空间中被**两次映射**（顶部+直接映射）。
  - 2. **内核栈页**：每个进程拥有独立内核栈，被映射在高地址，下方设**未映射的守护页**（PTE_V无效）；栈溢出会触发异常并使内核panic，避免覆盖其他内核内存导致运行异常。
- 内核栈既可通过高端内存映射访问，也可通过直接映射地址访问；若仅采用直接映射，设置保护页需取消虚拟地址映射，会导致物理内存难以正常使用。
  - 内核对跳板页与内核文本页配置`PTE_R`+`PTE_X`权限，用于读取与执行指令；其余页面设为`PTE_R`+`PTE_W`，支持读写操作。
  - 保护页的映射为无效状态。
- **跳板页**直接映射通常供内核态访问，确保内核能快速找到跳板页；顶部映射则映射到用户态地址空间的高地址，让用户态程序在触发特权级切换时能通过这个地址跳转到内核代码。这种双重映射能兼顾内核态的直接访问需求和用户态到内核态的切换效率。
- fork 创建子进程时，会复制父进程的页表，但物理内存通过写时复制共享，不会立即开辟新物理页。需要单独为子进程开辟的是内核栈，供子进程进入内核态时使用；还有进程控制块，记录子进程的 PID、状态等信息。用户态虚拟地址空间看似复制，实际物理内存到子进程写入时才分配新页。

- 调用 **kalloc** 分配物理页，随后向进程的页表中添加指向这些新物理页的页表项（PTE）。Xv6 会在这些页表项中设置 PTE_W、PTE_R、PTE_U 与 PTE_V 标志位。大多数进程并不会使用整个用户地址空间，Xv6 会将未使用的页表项的 PTE_V 标志位清零。
- sbrk is the system call for a process to shrink or grow its memory.
- **exec**:exec is a system call that replaces a process’s user address space with data read from a file, called
a binary or executable file. A binary is typically the output of the compiler and linker, and holds
machine instructions and program data.
  - **exec** 是一种系统调用，作用是用可执行文件（二进制文件）的数据替换进程的用户地址空间。
  - exec 先通过 namei 打开指定二进制文件，再读取其 ELF 头部。
  - Xv6 采用通用 ELF 格式，文件结构为 ELF 头（elfhdr）+ 程序段头（proghdr）序列。
  - Xv6 程序包含两个程序段，分别对应指令和数据。
  - 第一步快速校验文件是否可能为ELF二进制文件。
  - ELF二进制文件以4字节魔数`0x7F, 'E', 'L', 'F'`（即ELF_MAGIC）开头。
  - 若ELF头部魔数正确，exec即认为该二进制格式合法。
  - exec 执行流程要点：
    1. 调用 `proc_pagetable` 分配无用户映射的新页表；
    2. 通过 `uvmalloc` 为各 ELF 段分配内存；
    3. 调用 `loadseg` 将各段加载至内存；
    4. `loadseg` 借助 `walkaddr` 获取物理地址，通过 `readi` 从文件读取数据。
  - 如何checker ？
    - 地址溢出检查 if(ph.vaddr + ph.memsz < ph.vaddr)：确保程序头中 vaddr + memsz 不会超过 64 位无符号整数的范围。如果发生回绕（例如 vaddr = 0xfffffffffffff000，memsz = 0x1000，和变成 0），则拒绝加载。
    - 段地址对齐与范围检查：确保 ph.vaddr 是页对齐的（通常 PAGE_SIZE），并且 ph.memsz 不会导致超出用户地址空间的最大地址（例如 RISC‑V Sv39 中用户空间最大为 0x3fffff000）。
    - 权限检查：只允许 PT_LOAD 类型的段，并且根据 flags 设置正确的 PTE 权限（r-x 或 rw-），不允许同时可写可执行（W^X）。
    - 单独的内核页表：在 RISC‑V 版本中，内核拥有独立的页表，用户进程的页表不包含内核内存映射。因此，即使恶意 ELF 指定 vaddr 等于某个内核地址，loadseg 也会因为用户页表中没有对应映射而失败（或者写入的是用户页表自身的物理页，不会触及内核）。这从根本上隔离了用户与内核。

#### real world
- xv6 借助分页硬件实现内存保护与地址映射，但其分页应用远不如主流操作系统复杂（后者会结合页异常机制，第4章详述）。
- xv6 内核采用虚拟-物理地址直接映射，并假定内核加载于物理地址 0x8000000，适配 QEMU 但不适用于真实硬件；成熟内核会通过页表适配硬件物理地址布局。
- RISC-V 支持物理地址保护与超大页，xv6 均未使用；小页适合内存紧张场景，大页可降低页表开销，适合大内存环境。
- xv6 内核无小型对象内存分配器，仅分配 4096 字节块，无法使用需动态分配的复杂数据结构，真实内核需支持大小块分配。
- 内存分配核心问题为高效利用有限空间与应对未知请求，当前更注重分配速度而非空间利用率。

#### QA
  - 为什么需要页表 ？
      #### 📚 问题：为什么需要多级页表？
      一级页表就像一个**超长的固定清单**，上面列出了整个虚拟地址空间里**每一个可能的页码**对应的物理位置。即使某个页码从来没被使用过，这个清单里也得为它留一个空位。
      这会导致巨大的浪费——以你提到的 SV6（32位、4KB页）为例：
      - 虚拟地址空间 = 2^32 字节 = 4GB
      - 每页 4KB → 一共需要 2^20 个页表项（约 104 万个）
      - 每个页表项 4 字节 → 一个页表占用 **4MB**
      4MB 看起来不大？但每个进程都有自己的页表。100 个进程就是 **400MB**。早期内存总共才几十 MB，这根本不现实。
      #### 🧠 两级页表的思路：按需分配
      两级页表不再一次性把整个清单建好，而是拆成两个层次：
      - **第一级（页目录）**：一张“大表”，记录每个“大块”区域是否存在。
      - **第二级（页表）**：只有当一个“大块”区域真正被使用时，才为它分配一张“小表”，记录这个块内部的详细映射。
      > 类比：  
      > 一级页表 = 一本有 100 万个条目的电话簿，每个人（即使没电话）都占一行。  
      > 两级页表 = 先查“区号表”，只有某个区号下有人，才去拿该区的详细电话簿。
      #### 💡 为什么能省内存？
      以你举的例子：一个进程只用了 **1MB 内存**（256 个页面）。
      ##### 一级页表：
      - 必须建好全部 104 万个条目 → 固定 **4MB**
      ##### 两级页表（以常见 10-10-12 分页为例）：
      - 页目录（第一级）：1024 个条目，固定占用 **4KB**
      - 该进程只用了 1MB，这 1MB 落在页目录的 **1 个条目** 范围内
      - 只需要为这一个条目分配一张二级页表（1024 个条目，4KB）
      - 这张二级页表里，只有前 256 个条目有效（后面 768 个为空，但整张表已分配）
      总占用 = 4KB（页目录）+ 4KB（二级页表）= **8KB**
      **8KB vs 4MB** → 节省了 **500 倍** 的内存。
      #### 🔁 多级页表真的“解决地址不连续”吗？
      你原来的说法“一级页表能解决地址不连续问题”其实需要修正一下：
      - **一级页表本身也能映射不连续的物理地址**（每个页表项可以指向任意物理页）。
      - 它的真正问题是：**页表自身太大**。
      - **多级页表解决的不是“地址不连续”，而是“页表太大”**。它通过“按需分配”二级页表，大幅降低了内存开销。
      #### 📊 一个更直观的对比表
      | 项目 | 一级页表 | 两级页表 |
      |------|----------|----------|
      | 地址映射能力 | 支持不连续物理地址 ✅ | 支持不连续物理地址 ✅ |
      | 页表内存占用 | 固定 4MB（32位/4KB页） | 按需分配，小很多 |
      | 1MB 进程占用 | 4MB | 约 8KB |
      | 100 个进程占用 | 400MB | 约 0.8MB + 共享页目录 |
      #### ✅ 总结一句话
      > **一级页表已经能解决虚拟地址到物理地址的不连续映射，但它自身太占内存。多级页表通过“按需分配”二级页表，把页表的内存开销从“虚拟地址空间大小”降为“实际使用大小”，这才是它的核心优势。**
