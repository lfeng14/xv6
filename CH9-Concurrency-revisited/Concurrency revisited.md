# Chapter 9: Concurrency revisited

## 概述

本章回顾并扩展了并发和锁的内容，讨论更高级的并发模式和技术。

## 9.1 锁模式（Locking patterns）

### 锁应该保护什么？

锁应该保护不变量（invariants）：
- 不变量是关于数据结构的声明，在操作之间保持为真
- 操作可能临时破坏不变量，但完成时必须恢复
- 锁确保一次只有一个操作访问数据结构

### 锁的粒度指南

1. **从粗粒度开始**：使用一个锁保护整个模块
2. **分析竞争**：如果锁成为瓶颈，再细化
3. **保持简单**：细粒度锁更复杂，更容易出错

### 何时使用锁

| 情况 | 是否需要锁 |
|-----|-----------|
| 读/写另一个CPU可能修改的数据 | 是 |
| 读/写当前CPU可能在中断中修改的数据 | 是 |
| 只在当前CPU的进程上下文中读/写数据 | 否 |
| 只读数据（初始化后从不修改） | 否 |

### xv6中的锁使用示例

#### 例子1：进程表

```c
// ptable.lock 保护:
// - proc.state
// - proc.parent
// - 进程表的分配/释放
```

#### 例子2：缓冲区缓存

```c
// bcache.lock 保护:
// - buf.refcnt
// - buf LRU链表
//
// buf.lock 保护:
// - buf.valid
// - buf.disk
// - buf.data
```

### 锁的职责规则

1. **如果一个函数返回一个对象的引用（或指针），它必须确保对象保持存在（引用计数递增或被锁保护）**
2. **如果一个函数释放了对对象的最后一个引用，它必须确保对象不会被并发访问**

## 9.2 类锁模式（Lock-like patterns）

### 引用计数（Reference counts）

引用计数可以视为一种锁的形式：
- 递增/递减必须是原子的
- 当计数为零时，可以安全释放对象

例子：inode引用计数
```c
// ip->ref 受 icache.lock 保护
// ref > 0: inode 正在使用
// ref = 0: inode 可以回收
```

### 条件同步（Condition synchronization）

`sleep()`和`wakeup()`是条件同步的形式：
- 等待条件变为真
- 当条件可能改变时唤醒

`sleep`/`wakeup`模式：
```c
// 等待方
acquire(&lock);
while(condition == false)
  sleep(chan, &lock);
// ... 使用资源 ...
release(&lock);

// 通知方
acquire(&lock);
condition = true;
wakeup(chan);
release(&lock);
```

### 通道（Channels）

通道是更高层的同步原语：
- 发送者向通道发送消息
- 接收者从通道接收消息
- 如果没有接收者，发送者阻塞
- 如果没有消息，接收者阻塞

通道示例（概念性）：
```c
// 发送
channel_send(ch, data);

// 接收
data = channel_recv(ch);
```

## 9.3 完全无锁（No locks at all）

### 无锁编程（Lock-free programming）

使用原子操作而不是锁：
- `load_linked`/`store_conditional`（LL/SC）
- `compare_and_swap`（CAS）
- `fetch_and_add`

无锁编程的挑战：
- 非常复杂
- 需要仔细考虑内存排序
- 难以测试和调试
- 通常性能收益不大

### 每个CPU的数据（Per-CPU data）

如果数据结构只被一个CPU访问，则不需要锁：
- 每个CPU的栈
- 每个CPU的空闲内存链表（某些分配器）
- 每个CPU的统计计数器

示例：每个CPU的统计
```c
struct cpu {
  // ...
  uint64 n_irq;  // 此CPU处理的中断数
  // ...
};
```

### RCU（Read-Copy-Update）

RCU模式：
- 读取者无锁访问
- 更新者创建副本，修改副本，原子地替换指针
- 等待所有可能的旧读者完成后释放旧版本

RCU在Linux内核中广泛使用。

## 9.4 并行性（Parallelism）

### 可扩展性（Scalability）

理想的可扩展性：
- 双倍CPU = 双倍性能（线性扩展）
- 但锁竞争会限制可扩展性

### 阿姆达尔定律（Amdahl's Law）

如果一个程序的S部分是串行的，那么使用N个CPU的最大加速比是：

```
加速比 ≤ 1 / (S + (1-S)/N)
```

示例：
- S = 0.5（50%串行）
- N = ∞
- 最大加速比 = 2

### 优化可扩展性

1. **减少锁持有时间**
   - 在持有锁之前完成尽可能多的工作
   - 尽快释放锁

2. **细粒度锁**
   - 将大锁拆分为多个小锁
   - 减少不同操作之间的竞争

3. **每个CPU的数据结构**
   - 避免共享
   - 定期合并结果

4. **无锁数据结构**
   - 复杂但有时必要

### xv6的可扩展性限制

xv6不是为高可扩展性设计的：
- `ptable.lock`：单个锁保护所有进程
- `bcache.lock`：单个锁保护缓冲区缓存
- `kmem.lock`：单个锁保护内存分配

真实系统（如Linux）使用更细粒度的锁。

## 并发设计检查表

### 设计并发代码时的问题

1. **共享什么数据？**
   - 识别所有共享数据
   - 考虑是否真的需要共享

2. **用什么锁保护？**
   - 每个共享数据应该被一个锁保护
   - 清楚地记录锁和数据的关系

3. **锁的粒度是否合适？**
   - 从粗粒度开始
   - 测量竞争，再细化

4. **锁顺序是否一致？**
   - 定义全局锁顺序
   - 始终按顺序获取锁

5. **是否有死锁风险？**
   - 检查锁获取循环
   - 确保没有循环等待

6. **中断安全吗？**
   - 如果锁在中断中使用，获取时必须禁用中断

7. **是否正确使用了sleep/wakeup？**
   - 检查条件是否在锁保护下检查
   - 检查是否使用了while循环而非if

8. **引用计数正确吗？**
   - 检查递增/递减是否原子
   - 检查没有遗漏引用

9. **数据竞争吗？**
   - 使用工具（如ThreadSanitizer）检查
   - 手动检查所有共享访问

10. **可以测试吗？**
    - 编写压力测试
    - 在多个CPU上测试
    - 尝试触发竞争条件
