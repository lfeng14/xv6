##### 整个调度流程可以分成几个步骤：
第一，当前进程准备让出 CPU 的时候，需要先获取自己的进程锁，把状态从 RUNNING 改成 RUNNABLE 或者 SLEEPING 等，确保状态改变过程中不会被别的 CPU 干扰。

第二，然后主动调用 sched，这会触发上下文切换到 scheduler 进程。在切换前，当前进程的锁要保持住，直到切换完成后再释放。切换到 scheduler 相当于 CPU 进入一个专门挑选下个进程的函数。

第三，scheduler 会获取 CPU锁，确保这个 CPU 正在安全地选择下一个进程。它会在就绪队列里找到一个 RUNNABLE 的进程，然后先锁住这个新进程的进程锁，更新它的状态为 RUNNING。

第四，scheduler 决定好要切换到哪个进程后，再进行第二次上下文切换，从 scheduler 切到目标进程。切换完成后，释放 CPU 锁，让目标进程在这个 CPU 上运行。

整个过程就是这么两次上下文切换和多重锁保护，确保调度过程安全、有序。
***

场景：  
当前 CPU 上在跑 **进程 A 的用户态代码**，调度器最后会选中 **进程 B** 来接班。

***

## 0. 用户态 A 在跑

- 运行位置：用户态代码（A 的 user stack）。  
- 栈：A 的用户栈。  
- 锁：没有持有任何内核锁（包括 p->lock）。  
- c->proc：指向 A。  
- p->state(A)：RUNNING。  

此时比如 A 调用了某个系统调用，或者被定时器中断，进入内核。

***

## 1. 用户态 A → 内核（trap 进入）

- 触发：  
  - A 发起系统调用，执行 `ecall`；或者  
  - 定时器中断把它打断。  
- 步骤（简化）：  
  - 硬件切换到内核态，跳到 `uservec`，保存用户寄存器到 A 的 **内核栈** 上。  
  - 最终进入 `usertrap()` / `syscall()` 等 C 函数。  
- 运行位置：A 的 **内核线程**（C 代码），用的是 A 的 kstack。  
- 栈：A 的内核栈。  
- 锁：还没有拿 p->lock。  
- c->proc：仍然指向 A。  
- p->state(A)：仍然是 RUNNING（因为还没准备放弃 CPU）。

***

## 2. A 决定让出 CPU：调用 `yield()`

在某个内核路径上（比如 timer interrupt 中的 `yield()` 或系统调用中主动调用 `yield()`）：

```c
void yield(void) {
  struct proc *p = myproc();     // 得到 A
  acquire(&p->lock);             // 1
  p->state = RUNNABLE;           // 2
  sched();                       // 3
  release(&p->lock);             // 8（注意：这句很晚才真正执行）
}
```

### 状态细节：

- 运行位置：仍在 A 的内核栈上。  
- 这一步做了三件关键事：  
  1. `acquire(&p->lock)`：拿到 A 的 p->lock。  
  2. `p->state = RUNNABLE`：声明「我准备好让调度器再次选择我，但现在我要下台」。  
  3. 调 `sched()`：把「剩下的换人动作」交给 sched。  
- 此时：  
  - 栈：A 的内核栈。  
  - 锁：A 的 p->lock 已经被 A 自己拿着。  
  - c->proc：还是 A。  
  - p->state(A)：刚被改为 RUNNABLE（逻辑上已不在跑，但实际上还在用自己的内核栈）。

为什么这里必须持有 p->lock，前面已经讲过：防止其他 CPU 的 scheduler 在你刚设 RUNNABLE 但还没真正停下使用内核栈时，又把你调度起来。 [xv6-guide.github](https://xv6-guide.github.io/xv6-riscv-book/Ch7.S3.html)

***

## 3. 在 A 的内核栈上执行 `sched()`

`sched()`（删去部分细节）：

```c
void sched(void) {
  struct proc *p = myproc();
  int intena = mycpu()->intena;

  // 这里会断言：必须持有 p->lock，且除了 p->lock 没有其它锁，
  // 并且当前 state 不是 RUNNING。
  // 以及中断是关着的（noff == 1）。

  swtch(&p->context, &mycpu()->context);  // ★ 核心调用
  mycpu()->intena = intena;
}
```

- 运行位置：仍然在 A 的内核栈上。  
- 栈：A 的内核栈。  
- 锁：A 的 p->lock 仍然被 A 持有。  
- 接下来这一行是关键：  

```c
swtch(&p->context, &cpu->context);
```

含义：  
- 把「当前 CPU 寄存器」保存到 A 的 `p->context`；  
- 从 `cpu->context` 恢复出 scheduler 线程上次的寄存器状态，切到 **scheduler 的栈** 上；  
- 返回后，执行点不再是 sched 的下一行，而是 **之前 scheduler 调 swtch 的那一行之后**。

***

## 4. `swtch`：A 内核栈 → scheduler 栈

`swtch` 做的事情（抽象）： [youtube](https://www.youtube.com/watch?v=-O_JX5mMMHY)

- 保存当前寄存器（包括 sp、ra 等）到 `*old`（这里是 A 的 `p->context`）。  
- 从 `*new`（这里是 `cpu->context`）恢复另一条线程的寄存器。  
- 因为恢复出的 ra 是「scheduler 上次调用 swtch 的返回地址」，所以 `swtch` 返回时，就落在 **scheduler 函数中**，并且用的是 scheduler 的内核栈。

切换完成后的世界：

- 运行位置：scheduler 线程的 C 代码。  
- 栈：scheduler 专用的内核栈（每 CPU 一份）。  
- 锁：注意，**A 的 p->lock 仍然被“逻辑上的 A 那条内核线程”持有**；只是现在 CPU 正在执行 scheduler 的那条线程。换句话说，p->lock 从「调用 swtch 的线程」传给了「被切出的上下文」，后面 scheduler 会负责在合适时机释放它。 [cnblogs](https://www.cnblogs.com/weijunji/p/xv6-study-13.html)
- c->proc：此时 scheduler 会先把 `c->proc` 设为 0 或维持原值，随后切换流程会调整。  

可以把这一步记成：  
> CPU 从「跑 A 的内核线程」跳到了「跑本 CPU 的 scheduler 线程」，但 A 的 p->lock 还在那边的 context 上没放。

***

## 5. scheduler：选 B

scheduler 代码（核心部分）： [ithelp.ithome.com](https://ithelp.ithome.com.tw/articles/10307957?sc=rss.iron)

```c
void scheduler(void) {
  struct cpu *c = mycpu();
  c->proc = 0;
  for(;;) {
    intr_on();                    // 允许中断

    for(p = proc; p < &proc[NPROC]; p++) {
      acquire(&p->lock);
      if(p->state == RUNNABLE) {
        p->state = RUNNING;       // 1
        c->proc = p;              // 2
        swtch(&c->context, &p->context);  // 3
        c->proc = 0;              // 5
      }
      release(&p->lock);
    }
  }
}
```

假设这次扫描时，选中了 **进程 B**：

- scheduler 先 `acquire(&B->lock)`。  
- 看到 `B->state == RUNNABLE`，于是：  
  1. 把 `B->state` 设为 RUNNING。  
  2. `c->proc = B`，表示本 CPU 决定让 B 上台。  
  3. 调 `swtch(&c->context, &B->context)`：  
     - 保存 scheduler 当前寄存器到 `c->context`；  
     - 从 B 之前保存的 `p->context` 恢复 B 的内核线程寄存器。  

**这时 B 的 p->lock 仍然被 scheduler 持有**（直到 B 自己在适当时机释放）。这就是「锁在两个线程之间传递」的典型例子。 [pdos.csail.mit](https://pdos.csail.mit.edu/6.828/2021/slides/6s081-lec-threads.pdf)

***

## 6. `swtch`：scheduler 栈 → B 的内核栈

`swtch(&c->context, &B->context)` 做完之后：

- 运行位置：B 之前停下来的地方 —— 也就是 B 当初调用 `sched()` 中的那次 `swtch` 返回之后。  
- 栈：B 的内核栈（`sp` 恢复为 B 内核线程的值）。  
- 锁：B 的 p->lock 仍然被「当前执行的这条内核线程（即 B）」持有。scheduler 那边（c->context）则暂存休眠。  
- c->proc：已经在前面被设为 B。  
- p->state(B)：现在是 RUNNING。  

换句话说：  
> 在 B 看来，自己只是调用了一次 `swtch(old, new)`，然后某个时刻“又返回了”，接着继续往下执行 `sched()` 后面的语句。

***

## 7. B 从 `sched()` 返回 → 回到 `yield()` → 回到 B 内核 / 用户态

对于 B 来说，它之前也调用过：

```c
yield();   // 或在 sleep/exit 等路径里调用 sched()
```

流程一样：  
- 在 `sched()` 中的 `swtch` 返回 → 恢复 B 的寄存器 → `sched()` 继续执行：  
  - 恢复 `intena`。  
  - `return` 回到调用者（比如 `yield()`）。  
- 回到 `yield()` 内部：  

```c
yield() {
  ...
  p->state = RUNNABLE;
  sched();              // 刚才这里返回
  release(&p->lock);    // 现在执行这一行
}
```

- 此时：  
  - B 仍在 B 的内核栈上。  
  - B 执行 `release(&p->lock)`，释放 B 的 p->lock。  
  - 然后 `yield()` 返回，回到上层内核逻辑；最终 `usertrapret()` 把 B 切回用户态，恢复 B 的用户寄存器和用户栈，回到 B 的用户代码。  

所以链路收尾是：  

- B 内核栈：`sched()` → `yield()` → 其他内核逻辑 → `usertrapret()`。  
- 最终：回到 **B 的用户栈 / 用户态指令**。

***

## 整条时序串起来（带“在哪个栈、谁持锁”）

1. A 用户态（A user stack，无锁）。  
2. trap 进入内核 → A 内核栈，无锁。  
3. `yield()`：  
   - `acquire(A->lock)`（A 内核栈，持 A->lock）。  
   - `A->state = RUNNABLE`。  
   - 调 `sched()`。  
4. `sched()`（A 内核栈，持 A->lock）：  
   - 调 `swtch(&A->context, &cpu->context)`。  
5. swtch：从 A 内核栈 → scheduler 栈，保存 A context，恢复 scheduler context（A->lock 逻辑上仍算被 A 的上下文持有）。  
6. scheduler（scheduler 栈）：  
   - 扫描找到 B，`acquire(B->lock)`，`B->state = RUNNING`，`c->proc = B`。  
   - 调 `swtch(&cpu->context, &B->context)`。  
7. swtch：从 scheduler 栈 → B 内核栈，保存 scheduler context，恢复 B context（B->lock 被当前线程持有）。  
8. B 的 `sched()` 返回（B 内核栈，持 B->lock）：  
   - `return` 回到 B 的 `yield()`。  
9. B 的 `yield()`：  
   - 执行 `release(B->lock)`，释放自己的 p->lock。  
   - 返回到更上层内核逻辑，最终 `usertrapret()` → B 用户态（B user stack）。  

**这就是你写的那条链：**  
用户态 A → 内核（A 内核栈）→ A 调 yield → sched → swtch → scheduler 栈 → scheduler 选 B → swtch → B 内核栈 → B 回到用户态。

- 或者专门画「p->lock 在这条链路中什么时候被谁拿、什么时候被谁丢」的简化表，帮助你背住这个不变量。  

#### QA
- 这里面有几把锁 ？

    你问的这个流程里，主要牵涉到几类「锁」，不是所有都长得一样，也不是都在同一层次上起作用。下面我们按「名字 + 作用 + 在这条链路中出现的位置」来梳理。
    
    ***
    ## 1. 进程锁：p->lock（最核心那把）
    **类型**：自旋锁（spinlock），`struct spinlock`。 [yibs](https://yibs.space/post/mit6s081-lab7-multithreading/)
    
    **保护的东西**：  
    - `p->state`（RUNNING/RUNNABLE/SLEEPING/ZOMBIE/UNUSED）  
    - `p->chan`（sleep 等待的 channel）  
    - `p->killed`、`p->xstate`、`p->pid` 等  
    
    **在这次「A → scheduler → B」链路里的作用：**
    
    - A 调 `yield()` 时：  
      - `acquire(&A->lock);` → 把 A 的状态改成 RUNNABLE。  
      - 这时 A 还在用自己的内核栈，但 p->state 已经不再是 RUNNING。  
    - `sched()` 被调用时：要求「必须**已经**持有 p->lock」，并且 state 不是 RUNNING。 [ithelp.ithome.com](https://ithelp.ithome.com.tw/articles/10307957)
    - `sched()` 里 `swtch(&A->context, &cpu->context)` 把 CPU 切到 scheduler：  
      - 注意：**A->lock 没有被释放**，而是“跨线程传递”：  
        - 调用 swtch 的那条内核线程是 A；  
        - 切过去后，CPU 在跑 scheduler 线程，但 A->lock 仍然是「A 这条被切出的线程」的锁。  
    - scheduler 选 B 时：  
      - `acquire(&B->lock);`，把 B 从 RUNNABLE 改成 RUNNING，`c->proc = B`，再 swtch 到 B。  
    - B 的 `sched()` 返回到 `yield()`，在 `yield()` 的最后一句：  
      - `release(&B->lock);`，此时 B 已经完全「接管 CPU」，不变量恢复正常。  
    
    **直觉记忆：**  
    - p->lock 是「**进程级的主锁**」，围住的是：  
      > 这个进程当前处于什么状态、在谁的栈上跑、哪个 CPU 认为自己在跑它。  
    - 在整条链路中，它的特别之处是：  
      - acquire 和 release **不在同一条调用栈里**，而是在 A 内核线程 ↔ scheduler ↔ B 内核线程之间传递，这就是 xv6 说的「不遵循谁加锁谁解锁的常规」那一节。 [xv6-guide.github](https://xv6-guide.github.io/xv6-riscv-book/Ch7.S3.html)
    
    ***
    ## 2. CPU 锁 / 中断嵌套：`push_off` / `pop_off` / `mycpu()->noff`
    这不是一把「显式命名的锁」，但语义上是 **“禁止本 CPU 被中断抢占”** 的机制。 [yibs](https://yibs.space/post/mit6s081-lab7-multithreading/)
    
    - 典型用法：`yield()` / `sched()` / `myproc()` 前都会通过 `push_off()` 把中断关掉（增加 `noff` 计数）。  
    - 在 `sched()` 中会断言：  
      - 当前中断是关闭的（`noff == 1`），避免在还没切完栈/状态时被 timer 再打断一次。  
    - 从效果看，它像是 **“本 CPU 的一把隐形锁”**：  
      - 保证在执行 `sched` 和 `swtch` 这些敏感代码时，不会有新的中断进来插一脚。  
    
    这一套主要是为了解决：  
    - 「在 swtch 期间被 timer 再打断，导致 re-entrant swtch」这一类诡异情况。  
    
    ***
    ## 3. 等待条件的那把锁：sleep 的 `lk`（条件锁）
    在你刚才那条链路里只用了 `yield()`，所以还没看到它。  
    一旦用到 `sleep(chan, lk)`，这把锁就登场了。 [mes0903.github](https://mes0903.github.io/OS/xv6-riscv-book-zh-TW/chapter7/)
    
    **lk 是谁？**
    
    - 具体调用里，lk 可以是：  
      - pipe 用的 `pi->lock`；  
      - semaphore 示例里的 `s->lock`；  
      - wait/exit 里的 `wait_lock` 等。  
    - 它不固定是某种结构，但语义很固定：  
      - **保护“条件”本身**，比如 buffer 是否空、子进程是否退出等。  
    
    **sleep(chan, lk) 的内部锁顺序（简化）：**
    
    1. 调用者在进入 sleep 前，已经持有 `lk`（这是调用约定）。  
    2. sleep 内部：  
       - 先 `acquire(&p->lock);`（拿当前进程自己的 p->lock）。  
       - 然后 **release(lk)**：此时仍然持有 p->lock。  
       - 设置 `p->chan = chan`，`p->state = SLEEPING`。  
       - 调 `sched()` → 切到 scheduler。  
    3. 将来被 `wakeup(chan)` 唤醒后，sleep 从 `sched()` 返回：  
       - 重新 `acquire(lk);`  
       - 再 `release(&p->lock);`，返回给调用者。  
    
    **它的作用：**
    
    - 和 p->lock 一起，防止「lost wakeup」：  
      - 在「条件检查 + 决定 sleep」这段时间内，要么你还 hold 条件锁 lk，要么已经 hold p->lock；  
      - 唤醒方在 `wakeup(chan)` 中会拿每个候选进程的 p->lock，而且通常在持有条件锁或其之后调用 wakeup；  
      - 于是 **检查条件、入睡、被唤醒** 整个过程不会错过对方的时刻表。  
    
    在你关注的 `yield()` 那条链路里，没有 `lk` 参与；一旦是 `sleep` 版本，链路会变成：  
    - 调用者持 `lk` → sleep 里接力 p->lock → 释放 `lk` → 调 `sched` 切走 → 将来醒来后再拿回 `lk`。  
    
    ***
    ## 4. 全局等待锁：`wait_lock`
    这把锁出场在：`wait()` / `exit()` / `reparent()` / `wakeup(parent)` 这些和父子进程关系相关的路径。 [mes0903.github](https://mes0903.github.io/OS/xv6-riscv-book-zh-TW/chapter7/)
    
    **用途：**
    
    - 保护 `p->parent` 字段（父子关系）。  
    - 更重要：作为 **wait/exit 的“条件锁”**，配合 sleep/wakeup 保证：  
      - 父进程在 wait 中 sleep 时，不会错过子进程 exit 的 wakeup；  
      - parent 和 child 同时 exit 时，不会互相死锁，init 能可靠地接管孤儿进程。  
    
    **在调度链路中的间接作用：**
    
    - 当 `exit()` 最终走到 `sched()` 永久放弃 CPU 时，它是同时持有 `wait_lock` 和 自己的 `p->lock` 去调用 `sched()` 的（按固定顺序），避免父子之间的并发 exit/wait 出现死锁。  
    
    你那条「用户态 A → scheduler → B」的基础图，只用 yield，不涉及 wait/exit，所以 `wait_lock` 在那条具体路径上没有直接出现，只是这个大体系中的一员。
    
    ***
    ## 5. pipe 的锁 / 其他子系统锁（作为条件锁使用）
    像 pipe 、semaphore 示例里的 `s->lock` 等都是同一种模式： [cnblogs](https://www.cnblogs.com/weijunji/p/xv6-study-13.html)
    
    - 类型：自旋锁。  
    - 保护的内容：具体子系统的数据结构（如管道缓冲区、读写计数）。  
    - 在 sleep/wakeup 模式下，它们充当 `lk`（上面说的条件锁）：  
      - 在检查 buffer 空/满、修改计数、调用 sleep 和 wakeup 时，都围在这把锁的保护下。  
    - 它们不直接参与「A 内核栈 ↔ scheduler ↔ B 内核栈」这条基本调度路径，但在「进程为何要 sleep / 何时被唤醒」上起作用。  
    
    ***
    ## 6. 小结：在你那条「A → scheduler → B」时间线上，真正参与的锁
    如果只看这条简化路径（A 通过 yield 让出 CPU，scheduler 选 B）：  
    
    1. **p->lock（A 的锁）**  
       - 在 A 的 `yield()` 中被 acquire。  
       - 在 A 的 `sched()` 里，带着这把锁执行 `swtch`，锁跨线程传递。  
       - 在 scheduler 把 A 调度出去、将来 A 再次被调度回来时，由 A 内核线程最终 release。  
    
    2. **p->lock（B 的锁）**  
       - scheduler 选 B 前 acquire；  
       - scheduler 在持有 B->lock 的情况下，把 B 从 RUNNABLE 变 RUNNING，并 swtch 到 B；  
       - B 从自己的 `sched()` 返回到 `yield()`，最后 release 自己的 p->lock。  
    
    3. **中断关闭机制（per‑CPU “锁”）**  
       - 在 `yield()`/`sched()` 入口时通过 `push_off()` 关中断，保证在「状态转换 + swtch」这段临界区内不会被 timer 再打断。  
       - 类似于「对当前 CPU 做的互斥」，防止 re-entrant 调度。  
    
    其他锁（wait_lock、pipe->lock、sleep 使用的条件锁 lk）在这条具体链路里不出现，但在 sleep/wakeup、wait/exit 这些更复杂情形下发挥作用。
